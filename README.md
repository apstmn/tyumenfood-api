# ТюменьFood — платформа-посредник для доставки готовой еды

Рабочий прототип сайта-маркетплейса ресторанов Тюмени: витрина с меню, корзина
и оформление заказа, кабинет ресторана-партнёра, кабинет платформы (ваш) и
слой интеграций с агрегаторами и платёжными системами. Комиссия платформы
7% считается и удерживается автоматически с каждого оплаченного заказа.

**Важно понимать сразу**: это рабочий, запускаемый прототип, но оплата и
интеграции с агрегаторами внутри него — честная демо-имитация. Ниже подробно
расписано, что уже работает по-настоящему, а что требует реальных договоров и
ключей API от третьих сторон (Яндекса, банков-эквайреров и т.д.) — без этого
не подключится ни одна платформа в мире, это не вопрос кода.

## Быстрый старт

```bash
npm install       # один раз
npm run seed       # заполнить демо-данными (рестораны, меню, логины)
npm start           # запустить сервер: http://localhost:3000
```

Открыть в браузере:
- `http://localhost:3000/` — витрина (список ресторанов Тюмени)
- `http://localhost:3000/restaurant-admin.html` — кабинет ресторана (демо: `sytny` / `pass123`)
- `http://localhost:3000/platform-admin.html` — ваш кабинет посредника (демо: `admin` / `admin12345`)

В кабинете платформы есть кнопка «Отправить тестовый заказ» — она имитирует
приход заказа от Яндекс Еды/Купера/Broniboy через вебхук, чтобы вы увидели,
как это будет выглядеть в реальной интеграции.

## Что уже по-настоящему работает

- Каталог ресторанов и меню, корзина, оформление заказа на сайте.
- Автоматический расчёт и удержание комиссии платформы 7% с каждого заказа
  (сумма всегда пересчитывается на сервере из цен в базе — клиент не может
  подделать цену).
- Самовывоз с QR-кодом и цифровым кодом подтверждения выдачи заказа.
- Личный кабинет ресторана: приём заказов, смена статуса (принят → готовится
  → готов → забран/завершён), сводка выплат за вычетом комиссии.
- Ваш кабинет платформы: подключение новых ресторанов, включение/выключение
  агрегаторов по каждому ресторану, сводная выручка по комиссии, разбивка
  комиссии по источнику заказа (сайт / конкретный агрегатор).
- Приём заказов от агрегаторов через единый вебхук-эндпоинт
  `/api/webhooks/:aggregator` — с той же автоматической комиссией поверх.
- В кабинете платформы — блок «Реквизиты для приёма комиссии» (ИП/ООО, ИНН,
  р/с, БИК, банк) с возможностью редактирования, и живое обновление сводки
  каждые 5 секунд, чтобы видеть, как начисляется комиссия по мере поступления
  заказов. Реквизиты по умолчанию уже заполнены из вашей карточки предприятия.

## Что здесь — архитектурная заготовка, а не боевая интеграция

### Оплата (`server/services/payments/`)
Карта, СБП QR и «оплата при получении» в демо работают как имитация —
без этого нельзя показать сквозной сценарий. Реальный приём денег в РФ
всегда идёт через лицензированного эквайрера/платёжного агрегатора и требует
онлайн-кассы (54-ФЗ). В файлах `yookassa.stub.js` и `cloudpayments.stub.js`
оставлены заготовки с точным описанием, что нужно получить у провайдера
(shopId/secretKey и т.п.), чтобы заменить имитацию на реальные платежи.

Раз у вас уже есть юрлицо, но провайдера ещё нет — вот с чего обычно
начинают в РФ:
- **ЮKassa** (бывш. Яндекс.Касса) — самый быстрый старт для одного юрлица,
  много готовых интеграций с сайтами.
- **CloudPayments** — похожая модель, часто выбирают за гибкий Payments API.
- **Т-Касса (Т-Банк/Тинькофф Эквайринг)** — если у вас уже есть счёт в Т-Банке.

Все три поддерживают карты и СБП по QR. Оплату «при получении» (наличные,
переносной терминал курьера) эквайринг не проводит — это отдельный поток,
который в прототипе уже учтён: заказ создаётся, комиссия платформы фиксируется
сразу, а ресторан вручную отмечает заказ оплаченным после получения денег.
Обязательно свяжитесь с бухгалтером/юристом по вопросу онлайн-кассы (54-ФЗ)
для этого сценария — это не техническая деталь, а требование закона.

### Агрегаторы (`server/services/aggregators/`)
Файлы `yandexEda.js`, `yandexLavka.js`, `kuper.js`, `broniboy.js` — это
готовый каркас (интерфейс `syncMenu` + `normalizeIncomingOrder`), но без
реальных ключей API вызовы явно и осознанно выбрасывают ошибку с описанием,
что нужно получить у агрегатора. Подключение живых интеграций возможно
только после того, как каждый агрегатор одобрит ваше юрлицо как партнёра:

- **Яндекс Еда** — публичный партнёрский API: https://yandex.ru/dev/eda-vendor/doc/ru/.
  Регистрация через кабинет для бизнеса; на практике большинство ресторанов
  подключают Яндекс Еду через свою POS-систему (iiko, r_keeper, Quick Resto,
  Frontpad и т.п.) — это быстрее, чем писать интеграцию с нуля.
- **Яндекс Лавка** — в основном даркстор-модель, готовую еду сторонних
  заведений подключает точечно через тот же контур Яндекса для бизнеса;
  доступность для Тюмени нужно уточнять у менеджера Яндекса.
- **Купер** (бывший СберМаркет, ребренд 2024) — партнёрство через личный
  кабинет для бизнеса Купера, условия уточняются напрямую у них.
- **Broniboy** — активно работает в Тюмени, есть отдельная партнёрская
  программа для ресторанов; публичного самостоятельного API, как у Яндекса,
  в открытом доступе нет — интеграция обсуждается с их менеджерами.

**Важное предупреждение:** ни я, ни любой другой инструмент не может
технически «подключить» вас к этим сервисам в обход официального партнёрства
— доступ к их API выдают только после проверки и договора с вашим юрлицом.
Копирование или взлом чужого кода агрегатора или сайта конкурента (в том
числе то, что называют «вскрыть код») я сознательно не делал и не буду —
это нарушение закона об авторском праве и, что важнее, не даёт рабочей
интеграции, потому что чужой код всё равно завязан на чужую инфраструктуру
и ключи доступа, которых у вас нет и не будет.

## Структура проекта

```
server/
  db.js                     — схема SQLite (встроенный node:sqlite, без нативных зависимостей)
  seed.js                   — демо-данные (рестораны/меню/логины)
  services/
    commission.js           — расчёт и удержание комиссии 7%
    auth.js                 — хэширование паролей кабинетов
    payments/                — слой оплаты (card/sbp_qr/cash/terminal + заготовки под ЮKassa/CloudPayments)
    aggregators/             — слой интеграций (Яндекс Еда/Лавка, Купер, Broniboy)
  routes/
    public.js                — витрина и оформление заказа
    restaurantAdmin.js        — кабинет ресторана
    platformAdmin.js          — кабинет платформы (ваш)
    webhooks.js                — приём заказов от агрегаторов
public/                      — сайт (HTML/CSS/JS без сборщика, открывается напрямую браузером через сервер)
data/app.db                  — файл базы данных SQLite (создаётся автоматически)
```

## Дорожная карта до реального запуска

1. **Оплата.** Выбрать эквайрера/платёжного агрегатора (см. выше), подключить
   его API вместо демо-провайдеров, настроить онлайн-кассу под 54-ФЗ.
2. **Агрегаторы.** Подать заявки на партнёрство в Яндекс Еда, Яндекс Лавку,
   Купер, Broniboy; либо подключиться через общую POS-систему (iiko/r_keeper),
   которая уже интегрирована со всеми ними — часто это быстрее, чем прямой API.
3. **Юридическая модель комиссии.** Согласовать с юристом/бухгалтером форму
   агентского договора с ресторанами-партнёрами — как оформляется удержание
   7% с точки зрения налогов и договорных отношений.
4. **Хостинг и продакшн.** Перенести с локального SQLite на управляемую БД
   (например, Postgres) при росте нагрузки, задеплоить на сервер/облако с
   HTTPS, настроить резервное копирование.
5. **Мобильное приложение.** Текущий сайт — адаптивный и открывается с
   телефона в браузере. Нативное приложение для App Store/Google Play — это
   отдельный проект (React Native/Flutter поверх того же API), имеет смысл
   после того, как подтвердится спрос через сайт.
6. **Курьеры/самовывоз.** Логика самовывоза с QR-кодом уже реализована.
   Если понадобится собственная курьерская служба (а не только партнёрские
   агрегаторы) — потребуется отдельный модуль распределения заказов по курьерам.

## Безопасность перед реальным использованием

- Смените пароли из `seed.js` и `SESSION_SECRET` в `server/index.js` —
  сейчас это демо-значения "для показа".
- Не публикуйте `data/app.db` с реальными данными клиентов в открытый репозиторий.
- Добавьте HTTPS перед тем, как принимать реальные платёжные данные.
